## 验证证据

- 常规测试：45 passed，3 项真实模型测试默认跳过。使用真实 SQLite、文件和 Excel，仅普通测试中的 OCR 推理采用替身。
- 真实模型专项：3 passed，包含打印批号及中文七字段合成标签的 mobile/server 配置。七字段均得到候选，名称、批号、生产日期核对通过；不代表真实包装全字段准确率。
- 浏览器：Edge 上八组完整流程通过。包括真实 CPU OCR、分组、人工确认、Excel 下载后读回、待确认修改、移图与拖动、草稿刷新恢复、旧标签失效及空记录作废。保存测试延迟真实服务响应，验证等待期间不会接受会被覆盖的输入。
- Python 静态检查、格式检查和 JavaScript 语法检查通过；390px 页面无横向溢出。
- Wheel 构建通过，包含 HTML、CSS 和 JavaScript；不包含数据库、图片、模型或测试缓存。

CPU 试验条件：Windows 11，16 个逻辑处理器，15.8 GiB 内存，Python 3.12.14，PaddlePaddle 3.3.0，PaddleOCR 3.7.0。CPU 具体型号未取得。

同一张合成中文标签的热运行测得 mobile 约 2.4 秒、server 约 71.3 秒，仅作为本机配置选择依据；不同照片尺寸和拍摄质量会改变耗时。默认采用 PP-OCRv5 mobile，不据此承诺每日容量或多人性能。

## 最终审查与修复

独立审查发现四项重要问题，均已补回归测试并修复：

1. 修改旧来料批号可能回滚产品当前地址：保留未改动的历史产品版本引用。
2. 错误分组移空后仍永久进入导出：增加需操作人、原因的明确作废，保留历史；移图不会自动作废。
3. 保存等待期间继续输入会被覆盖：保存期间冻结编辑和切换，成功或失败后恢复操作。
4. 更正字段后旧区域标签可能重新成为有效样本：使相关标签失效，重新校对后才可采集。

另将“模板已有行样式被首行覆盖”按用户实际影响提高为重要项，补测试后改为保留已有行格式，仅扩展新行时复制样式。上述修复均有先失败后通过的回归证据；没有暂缓的小问题。

## 实施选择及影响

1. 在当前目录创建开发分支，保留原有需求文件，未另建工作树。影响：当前目录位于开发分支。
2. 按用户批准的计划采用本机图片副本、手填操作人、首次确认时间和确认快照导出。影响：试用后如调整规则，需相应修改界面和数据处理。
3. 业务材料缺失时使用合成照片和模板验证软件。影响：不能宣称真实识别和实际模板已验收。
4. 使用现有 Python 3.12 运行时创建独立环境，保留全局 Python 3.15。影响：换电脑仍需准备兼容解释器。
5. Windows 使用 PowerShell 与过程记录执行任务，代替技能中的 Bash 脚本。影响：复现命令以本项目说明为准。
6. 实际推理复现 oneDNN 兼容错误，因此关闭该加速配置。影响：可能牺牲推理速度，后续版本可重新验证。
7. 先稳定业务接口，再集中接入工作台。影响：中间阶段未独立交付界面，最终已接通。
8. 自动分组只处理同一次上传中的照片，避免相同产品和批号的不同次来料被合并。影响：分次补拍需人工归组。
9. 样本标签要求与具体区域完整文字对应，不能将跨行业务字段直接贴成单行标签。影响：需额外校对需要积累的区域文字。
10. 增加重复空记录作废以完成误分组更正；仅允许已确认且照片全部移出的记录。影响：历史保留，不能把有照片的记录直接作废，也不提供删除历史操作。
11. 缺少真实材料的效果和模板验收继续保留；企业访问、账号、多人、GPU、模型训练继续按原定范围后置。影响：当前只适合本机试用。
12. 本次实现保留在本地开发分支供试用，未自动合并或推送。影响：GitHub 暂不包含这些实现提交。
