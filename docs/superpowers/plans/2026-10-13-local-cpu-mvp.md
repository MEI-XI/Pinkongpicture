# Pinkongpicture 本地 CPU 测试版开发计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking. 用户已于 2026-10-13 批准按本文实施。

**Goal:** 在一台电脑上完成包装照片导入、PaddleOCR 识别、字段复核、产品归档、来料保存和固定模板 Excel 导出，并验证批量分组与纠错样本积累。

**Architecture:** 建议采用本机浏览器界面加 Python 本地服务。OCR 结果通过统一的文字与坐标结构交给提取、分组和复核功能；记录保存在本地数据库，原始照片与训练区域样本分别管理。先完成单条记录流程，再接入历史档案和批量自动分组。

**Tech Stack:** PaddleOCR、CPU、规则提取、Python、FastAPI、Jinja2、原生 JavaScript、SQLite、openpyxl、pytest。按用户批准的计划实施，已实测依赖组合并锁定版本。

**Spec:** [本地测试版 PRD](../../PRD.md)。执行者必须同时阅读 PRD 和本计划。

状态：用户已批准实施，本地 CPU 软件流程已通过行为、接口、真实模型和浏览器测试。真实照片、核实答案和实际 Excel 模板仍待提供。原始任务清单保留用于最终业务验收，不能用合成测试替代其中的真实资料检查。实施结果见 [本地测试版交付记录](../../IMPLEMENTATION_REPORT.md)。

实施与启动说明见 [本地试用说明](../../LOCAL_TEST_GUIDE.md)。

## 全局约束

- 首期为单机本地 CPU 测试，不搭建企业服务器、外网入口、登录权限或多人协作。
- 七个业务字段为产品名称、规格、生产厂商、生产地址、批号、生产日期、保质期；另记录入时间和操作人。
- 一条来料记录对应一次来料中的一个产品、一个批号，可关联多张照片；同产品同批号再次来料仍可新增记录。
- 每条记录必须人工确认后导出，历史资料不得直接覆盖本次图片内容。
- 规格不同或厂商变化建立新档案；仅地址变化，经确认建立档案新版本，旧记录保持原值。
- 包装未标注需说明原因；看不清需补拍或依据可核实资料补填，保留来源。
- 保存包装原文，只统一明确日期的格式，不反推缺失信息。
- 已确认记录修改后重新确认，保留修改历史，既有 Excel 文件不变。
- 首期只积累产品记忆和有效纠错样本，不训练模型、不引入语言模型。
- 包装图片、训练样本、数据库、模型和业务 Excel 均不提交 Git。
- “5 人同时操作、每组 3 张照片、约 15 秒”是后续多人阶段的待测目标，不是单机验收门槛。

## 优先复核的五类情况

1. 同款两个批号与没有批号的背面照片混在一起：不得错误合并，无法判定时待分组。由 T6 验证。
2. 字段已填写后移动照片：原组不能保留失去图片依据的确认状态，新组要重新整合候选。由 T6 验证。
3. 修改产品地址或已经导出的记录：旧记录快照、旧 Excel 不变，未确认修改不流入导出。由 T2、T4、T5 验证。
4. 手机照片旋转或缩放后生成字段定位与训练截图：文字区域必须对应正确图片，跨行地址不能强行做成一条单行标签。由 T1、T3、T7 验证。
5. 批号 00123、含糊日期、“见封口”和未标注说明：批号保持文本，不猜日期，说明按真实模板表达。由 T3、T4 验证。

## 已采用的实施建议

这些建议在用户批准按开发文档实施后采用。它们是本地版本的实施选择，试用后仍可调整。

| 决策 | 建议 | 理由与影响 |
| --- | --- | --- |
| 界面形式 | 本机浏览器页面，本地服务仅监听本机 | 方便做图片预览、字段定位和拖动分组，手机照片先传到电脑导入 |
| 前端复杂度 | Jinja2 页面加原生 JavaScript，不另建大型前端工程 | 先覆盖一个复核工作台和记录列表，减少安装与构建步骤 |
| 数据存储 | SQLite 保存业务记录和版本；图片放本地文件目录 | 单机无需另外部署数据库服务 |
| 本地原图保存 | 导入后复制到本机应用数据目录，用户源文件不动 | 浏览器无法长期可靠引用用户任意源路径；本地副本便于重启后复核，不是企业集中存图 |
| 操作人 | 本地设置姓名，确认前显示并允许更换 | 保留操作人字段，不引入账号系统；该姓名属于用户声明，不是登录认证 |
| 录入时间 | 首次确认保存时写入固定北京时间；修改时间单列存储 | 修改或重新导出不改变首次录入时间 |
| 日期筛选 | 首期按首次录入日期筛选，批次筛选按产品加批号 | PRD 尚无独立来料日期字段，不凭空新增 |
| 已确认记录再次编辑 | 保留上一确认版本；有待确认修改时提示，正式导出仍使用上一确认版本 | 实现“仅导出已确认内容”，重新确认后才切换最新版本 |
| CPU 调度 | 一个识别工作队列复用同一模型，界面显示逐图进度 | 先测单机资源和响应，避免每张图重载模型；不引入分布式队列 |

独立虚拟环境使用实测通过的 Python 3.12.14、PaddlePaddle 3.3.0、PaddleOCR 3.7.0 和 PP-OCRv5 mobile 模型。全局 Python 3.15 保持原样。当前 Windows 组合关闭 oneDNN，以避开已复现的推理兼容错误。

## 数据流与模块边界

实际处理顺序：逐图 OCR → 逐图提取产品与批号线索 → 建议分组 → 人工修正 → 组内整合七字段 → 历史产品匹配与差异复核 → 确认保存 → 导出与样本积累。

单条流程先由人员建立图片组，不等待自动分组完成。批量阶段复用同一 OCR 和提取结果，不能为了分组重复识别所有照片。

| 数据对象 | 最小内容与约束 | 首次定义任务 |
| --- | --- | --- |
| ImageAsset | 图片编号、本地位置、原始方向、显示坐标对应关系 | T1 |
| OcrBlock | 图片编号、文字块编号、原文、多边形坐标和识别分数 | T1 |
| FieldValue | 字段名、原文、规范值、来源类型、图片文字引用、缺失或补填说明 | T2 |
| ReceiptRevision | 来料编号、版本、七字段快照、图片组、产品版本引用、状态、操作人与时间 | T2 |
| FieldCandidate | 字段候选值、对应文字块、提取理由及冲突提示，保留多个候选 | T3 |
| ExportSelection | 录入日期范围、产品和批号筛选；只读取确认版本 | T4 |
| ProductVersion | 产品内部编号、版本号、名称规格厂商地址及生效记录 | T5 |
| GroupProposal | 图片编号集合、分组依据、冲突和待分组图片列表 | T6 |
| CorrectionSample | 样本编号、区域截图、正确文字、OCR 原文、来源图片和确认版本引用 | T7 |

业务字段可以跨多个文字块；训练样本则必须对齐具体文字区域。没有清晰区域依据的业务修改不生成训练样本。样本来自记录的确认版本，后续更正时应标记旧样本已被替代，不能将相互冲突的标签都标为有效。

**交付物：** 可执行的测试条件、样本索引和字段导出约定。此阶段可以不写应用代码。

- [ ] 核实目标测试电脑的操作系统、CPU、内存和可用磁盘；规划时读取硬件信息未成功，不能据此推断配置。
- [ ] 建议先准备 20—30 组真实产品照片，覆盖相似包装不同批号、跨行地址、小字、反光、未标注、委托方与生产商并存的情况。
- [ ] 由熟悉产品的人员核实七字段参考答案、图片所属产品和批号；部分产品及新拍照片留作最终验证，不参与调规则。
- [ ] 取得现有 Excel 模板和一份正确填写的示例，确认文件类型、工作表、数据起始行、公式样式和字段位置。
- [ ] 确认上表中的本地图像副本、操作人、时间、筛选及待确认修改导出规则。
- [ ] 确定模板如何表达“未标注”、原因、日期原文和统一日期；模板无对应位置时先记录待决，不自行增列。

## T1 本地 OCR 与图片导入

**文件：** 创建 pyproject.toml、requirements.lock、app/main.py、settings.py、domain.py、images.py、ocr.py、views.py、工作台页面及 tests/test_ocr.py。

**输入与输出：** recognize_image 接收 ImageAsset，返回 OcrBlock 列表和耗时；import_images 返回带稳定编号的 ImageAsset。模型参数集中配置，业务模块不直接依赖 PaddleOCR 返回对象。

- [ ] 创建行为测试：手机旋转图显示方向正确、OCR 框能映射到显示图片、单张识别失败时其他图片结果不丢失；运行测试确认尚未实现而失败。
- [ ] 在独立环境安装可兼容的 CPU 依赖，仅安装识别所需组件。用相同照片比较一套轻量配置和一套较高精度配置，选定后锁版本。
- [ ] 实现批量导入、稳定图片编号、模型复用、逐图进度，以及文字和位置展示；处理副本清理不触及用户源文件。
- [ ] 运行 python -m pytest tests/test_ocr.py；预期全部通过。用真实照片检查框位置，分别记录首次加载与模型已加载后的耗时。
- [ ] 对照 git diff 检查只提交代码和脱敏资料，提交一个可独立运行的导入识别版本。

**可见交付：** 浏览器中导入照片后能看到文字和位置；实际使用 CPU，无法识别时有明确状态。

## T2 单条记录与人工确认

**文件：** 创建 app/storage.py、records.py、记录页面、tests/test_records.py；扩展 domain.py、views.py 和工作台。

**输入与输出：** create_receipt 接收人工确认的图片组；confirm_receipt 接收七字段、来源说明和操作人，生成 ReceiptRevision；edit_receipt 生成待确认修改并保留上一确认版本。

- [ ] 创建行为测试：缺失说明、固定录入时间、保存后重开、同产品同批号再次来料、已确认记录修改后保留前后值；运行并确认失败。
- [ ] 建立本地数据库、人工建组和七字段表单，支持普通值、未标注与外部资料补填，不把空字符串自动解释成未标注。
- [ ] 实现确认和修改流程，保存当次字段快照与修改历史；确认与关联更新在一次事务中完成。
- [ ] 运行 python -m pytest tests/test_records.py；预期全部通过。手动关闭重开，确认记录与操作人仍可查看。
- [ ] 检查本地数据未进入 Git，提交可人工登记和追溯修改的版本。

**可见交付：** 即使自动提取暂未完成，也能对照图片完成一条真实来料记录。

## T3 七字段提取与证据复核

**文件：** 创建 app/extraction.py、tests/test_extraction.py；扩展 domain.py、records.py、工作台及其交互脚本。

**输入与输出：** extract_candidates 接收单图或已确认图片组的 OcrBlock，返回各字段的 FieldCandidate；人员选择或修改后形成 FieldValue。逐图候选可供 T6 分组使用。

- [ ] 创建行为测试：多行地址、委托方与生产商并存、规格候选冲突、批号 00123、含糊日期、“见封口”和未标注；运行并确认失败。
- [ ] 实现关键词与位置规则，保留多个候选、原始文字和规范值；缺乏依据时留待确认，不用历史值掩盖当前缺失。
- [ ] 接入自动预填、点击字段定位文字、候选选择、补填来源与未标注原因；跨行字段可引用多个文字块。
- [ ] 运行 python -m pytest tests/test_extraction.py tests/test_records.py；预期全部通过。用真实照片对照检查字段和来源位置。
- [ ] 提交具备自动预填与人工纠正的单条登记版本。

**可见交付：** 品控员能从“手工抄写”变为“检查预填并修改”，但每条记录仍需确认。

## T4 固定模板 Excel 导出

**文件：** 创建 app/excel.py、tests/test_excel.py；扩展记录页面、views.py。真实模板及导出结果放本地数据目录。

**输入与输出：** export_confirmed 接收 ExportSelection、模板位置和目标位置，读取 ReceiptRevision 的确认快照，返回导出文件及记录数量。

- [ ] 基于真实模板确定字段映射；先写行为测试：只导出确认版本、日期筛选、前导零、未标注说明、列位置、重复导出不向旧文件追加；运行并确认失败。
- [ ] 实现模板副本填写，保留经确认需要保留的格式与公式，导出到新文件；不覆盖模板和已导出的文件。
- [ ] 检查模板类型和保留要求。openpyxl 适配须以模板实测为准；若模板为旧版 .xls 或含无法保真的对象，先确定转换或其他适配方案。
- [ ] 运行 python -m pytest tests/test_excel.py tests/test_records.py；预期全部通过。重新读取结果核对值、行数和位置，并用 Excel 或用户实际办公软件检查版式。
- [ ] 提交首个“图片识别 → 人工确认 → 真实 Excel”完整流程。

**可见交付：** 用用户现有表格完成真实记录导出。没有真实模板时此任务不能标记完成。

## T5 产品记忆与档案版本
